Message lifecycle / Current implementation

消息记录、Agent 执行与恢复时序

按当前代码整理 App 如何先保存用户消息、如何把任务交给远端 Agent、Agent 如何落盘，以及 App 重启后如何重新读取并合并最近记录。

基于当前实现整理
更新：2026-07-14

01

本地先显示

点击发送后，用户消息和等待回复占位消息先进入设备本地，不需要等 SSH 或 Agent 返回。

02

Agent 负责后台可靠执行

每次任务都有独立 taskId，状态、输入、输出和时间都写入远端文件，即使 App 被关闭仍可继续。

03

重新连接后合并

App 先恢复本地历史，再按 conversationId 拉取 Agent 最近 5 个任务，以 taskId 去重并补入结果。

04

三层记录分别保存什么

三层记录不是重复设计：本地保证体验，Agent 保证任务恢复，CLI session 保证 AI 上下文连续。

设备层

App 本地消息

保存用户气泡、AI 气泡、运行状态、计时、附件和错误信息。

  • 每个会话最多 120 条
  • 消息正文最多约 60,000 字符
  • 先显示，再同步远端
可靠执行层

Agent 任务记录

~/.ai-workbench/agent/tasks/<taskId>/ 是远端任务的事实来源。

  • prompt.txt 与 command.b64
  • status、pid 和时间字段
  • output.log 与错误日志
AI 上下文层

Codex / Claude session

工作目录中的 session 文件只负责让 AI CLI 使用 resume 延续上下文。

  • Codex：*.session
  • Claude：*.claude-session
  • 不等同于 App 聊天记录
05

消息与会话如何对齐

App 用四类 ID 把本地气泡、Agent 任务与 AI CLI 会话连接起来。

ID作用生命周期主要用途
server.id左侧一张工作会话卡会话配置存在期间查找设备本地消息和配置
conversationIdAgent 逻辑会话多个任务共同复用跨重启、跨设备定位同一组任务
remoteTaskId一次远端任务每次发送创建一个查询状态、取消任务、消息去重
message.id一条 App 本地消息单条气泡生命周期更新占位消息和多窗口合并
CLI session IDCodex 或 Claude 自身上下文由对应 CLI 管理执行下一条任务时 resume
06

当前同步规则

这些数值决定消息什么时候刷新、为什么不会无限拉取，以及异常时如何恢复。

场景当前规则结果
当前运行会话约每 6 秒查询一次 Agent task 状态自动更新
所有会话约每 20 秒做一次后台同步检查自动恢复
App 启动约 1.2 秒后开始首次 Agent 同步补齐状态
最近历史每次读取 5 个任务按需加载
继续上拉使用 before 游标再读取更早 5 个增量分页
Agent runner 启动失败最多重试 2 次，特定启动故障再降级到 SSH兼容降级
直接 SSH 时关闭 App没有 Agent task 文件可供恢复不可可靠恢复
边界

目前跨设备同步依赖相同的 conversationId 和远端 Agent 记录。本地消息缓存不会自动跨设备复制；新设备只能从 Agent 拉到已由 Agent 执行并落盘的任务。
